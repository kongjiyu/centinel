# Project readiness — agreed implementation and acceptance

Readiness is a project-level background assessment, independent of Review execution and approval. It uses bearer-scoped Supabase persistence. Repository inspection is static; requirement, design, and coding-standard assessments use the configured Model Provider and source-grounded checks. No actor/permission completeness checklist and no semantic prefilter of requirement content. All selected readable source content is offered for assessment; an unsupported, unreadable, oversized or unavailable input must not become a Completed verdict.

## Contract

Follow-up: the open signed-in workspace now checks GitHub remote heads automatically; unchanged successful commits skip content import and reuse readiness. Local imports still require an explicit refresh after external edits. See [automatic GitHub sync](GITHUB_AUTOMATIC_SYNC_2026-10-20.md) for the bounded cadence, recovery and verification limits.

- GET /projects/:id/readiness returns the latest job status and last successful snapshot. It also checks for changed source versions and recovers pending work when the authenticated app reconnects.
- POST /projects/:id/readiness with {trigger:'manual'} queues/reuses an assessment and returns status (202). Project creation, import/upload batch completion, source sync/pull completion and removal queue automatic checks. Rapid events coalesce; publication checks source fingerprints so stale assessments cannot replace current ones.
- Operational states idle/queued/running/completed/failed are separate from category states Missing/Incomplete/Completed. Loading spinner and disabled Start are beside the title. Before a valid result, render a dash; on failure preserve the last result with retry feedback. No separate readiness screen or technical logs in the card.
- Snapshot categories: repository, requirements, design, standards. State reflects required checks, never file count. Repository availability/configuration checks do not run builds or arbitrary repository scripts. Semantic discovery can identify several document categories in one file; names/extensions are hints only.
- Assess requirements for clarity, consistency, testability, decision logic, constraints, exception and scope coverage. Assess design for explicit responsibilities/interfaces/data/flows/failure decisions supporting the scope. Assess standards for identifiable applicable rules, usable checking methods and conflicts; this is policy readiness, not code compliance.
- Each gap includes category, reason, action and verifiable source references where present, including source version and content hash. Missing content has no invented location. Full source bodies, model prompts and private reasoning are not journal metadata; concise, validated quotations are permitted as evidence, with common credential-like excerpts excluded. Readiness gaps appear in existing Project Findings with clear origin and immutable assessment context. Subsequent assessment replaces current gaps without rewriting history.
- Existing Review gates/workflow remain unchanged in this task. False-positive mitigation/domain evaluation are a separate proposal.

## Outcome acceptance follow-up

The strengthened policy is `readiness-2026-10-19.2`. It is part of the source fingerprint, so an older assessment is reassessed after the policy changes even when its sources do not. A semantic category must account for every supplied readable source, provide a classification basis and exact evidence for positive classification, and assess every named criterion. Each criterion retains a short evidence explanation and versioned references. Both passing and gap verdicts require exact source grounding; requirements consistency and coding-rule conflicts need two distinct quotations. Missing scope coverage may cite the source-backed scope item as its absence anchor. Unknown or mixed scope coverage stays unverified, and ungrounded gap claims become generic requests for evidence. Requirements/design scope and standards applicability require an explicit source-backed scope map; a blanket claim of coverage is insufficient. These explanations are evidence summaries, not private model reasoning.

The fixed corpus in `sidecar/src/readiness/fixtures/` has 11 independently labelled cases: complete material, a missing category, vague requirements, conflicting requirements, an untestable requirement, an exception gap, insufficient design, conflicting standards, code without documentation, misleading filenames, and embedded prompt injection. `evaluation.ts` compares production-engine states and all criterion verdicts with those labels and checks citation validity. Synthetic-provider tests validate the evaluator; they do not establish the model's accuracy. The gold labels are frozen before live execution. Alternative valid quotations are diagnostic differences rather than automatic failures.

`liveEvaluation.ts` runs the existing configured Codex model against fictional fixtures using the app-managed login, without modifying project data. It records the model, policy, corpus hash, case outcomes and safe failure codes under ignored `evidence/readiness-outcomes-2026-10-19/`. It stops the corpus after an execution failure rather than repeatedly calling a blocked provider. It does not export authentication, raw prompts, source bodies or private reasoning. Live provider execution failures remain failed acceptance cases, not Missing documentation results. The initial 11 execution failures are retained in `live-codex-pre-schema-fix.json`; a subsequent single-case attempt also failed. The independently isolated 429 cause is recorded in `provider-diagnostic.json`. The complete corpus hash is `07371a0a91bd07cf7e5df89f953ad50b1541efdf30a250d5b0de67d5c48b48a1`.

The local provider startup initially failed because Unix permissions did not protect its Windows credential directory. The adapter now applies protected Windows ACLs for the current user and SYSTEM; existing credential contents are preserved. A real repeat-call ACL inspection and provider regression tests passed. Unknown provider errors remain generic; trusted configuration, credential, context, timeout, malformed-response, persistence and changed-source failures have static actionable guidance and retain the previous successful snapshot.

Latest focused verification: **134 sidecar tests in 13 files**, **58 frontend tests in six files**, and sidecar type checking passed. The production frontend build and a Tauri debug build with embedded assets also passed. The built Windows executable was launched in the background and its native WebView rendered the sign-in page at `https://tauri.localhost/`; signed-in native readiness behavior is still unverified because that WebView has a separate session from the signed-in browser.

They correctly avoided Missing or Completed claims and fabricated locations. Finding selection showed its recommendation and immutable readiness context. This verifies a live unavailable-input/persistence/manual-trigger path, not successful model semantics or live negative membership checks.
