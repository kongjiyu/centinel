# Readiness review reliability — 2026-10-23

## Readiness

### Mitigation

Readiness now reads each selected artifact through its frozen project, artifact, and version identifiers. The authenticated reader checks project membership and performs one project-scoped immutable-version lookup, then validates the version's artifact ownership, private Storage path, selected content hash when it is a SHA-256 value, and downloaded bytes against the version hash. It does not query the mutable current artifact row or repeat the version lookup before downloading. Read cancellation reaches both the membership/version queries and Storage download.

Frozen source downloads use a four-worker pool. The pool writes results into the original source positions, passes one shared `AbortSignal` to every read, and stops scheduling new reads after cancellation. Unsupported binary formats and hash mismatches remain unavailable inputs with safe public messages. No source is silently dropped or replaced by a current version.

Semantic assessment preserves every readable input. It sends source batches sequentially, with no source summary or truncation: each batch contains at most 32 source segments and 64,000 source characters; larger artifacts are split at Unicode-safe boundaries and every segment is assessed. Batch responses must inventory every source ID in that batch. Results are merged only after every batch validates, and the combined inventory must cover every readable source. Provider calls remain sequential to avoid concurrent quota spikes. For 192 small artifacts this bounds the request count to six semantic assessments, followed by one cross-batch comparison when applicable; larger content may require more batches.

Requirements consistency and coding-standard conflict passes receive only exact, previously validated candidate quotations. Each comparison task has its own candidate index, and every citation names its batch number. A pass is accepted only when exact evidence covers every batch in which that category and criterion were present. Evidence from a different category or criterion, omitted relevant batches, malformed citations, oversized comparison candidates, and incomplete source inventory remain unknown or incomplete. A category is Missing only when every validated batch reports Missing, the full readable source inventory was examined, classification evidence is valid, and all Missing batches have unknown checks with empty evidence and empty scope inventories. Completed requires valid exact evidence for all required checks, complete source coverage, and a validated cross-batch pass when one is required.

Snapshots store a versioned, sanitized `validationDiagnostics` object: batch count, raw category presence, inventory/classification/shape/evidence validation flags, raw check-status counts, effective statuses, and cross-batch outcomes. It does not store model prompts, source bodies, model-private reasoning, or raw provider errors. Normal user-facing readiness findings may still retain validated excerpts as evidence.

The readiness policy version is `readiness-2026-10-23.1`. Diagnostics are additive fields in the existing assessment JSON; this mitigation adds no table, database migration, or alternate store. Provider failures, capacity pauses, and the assessment deadline fail the current job without replacing its previous successful snapshot. One 15-minute default deadline covers bounded source reads, every sequential batch call, cross-batch comparison, and final source revalidation. The coordinator factory accepts an optional job budget, clamped to a 1 ms minimum and explicit 20-minute maximum. The shared signal aborts outstanding Storage/model requests and prevents a later batch from starting. A run with too many or too-slow batches can still time out at the cap; the job then remains failed with its old snapshot and no partial batch result is saved. Readable-but-unavailable source entries continue through the established incomplete-coverage path and cannot produce Missing or Completed semantic categories.

### Verification and limits

Offline provider stubs verify a three-batch inventory, complete pass citations from all three batches, rejection of a pass citing only two batches, rejection of exact citations belonging to a different category/criterion, and safe all-batch Missing behavior. Coordinator tests verify at most four concurrent frozen reads, stable input ordering, successful sequential work lasting over three minutes, deadline cancellation, and preservation of the previous snapshot. Frozen-version reader tests verify exact project/version/artifact/hash ownership and that authorization, metadata checks, and byte-hash validation remain in the path. Targeted Readiness, frozen-reader, and concurrency tests passed; see task verification for the exact command and count.

These tests do not establish live model accuracy, live Supabase/RLS behavior, the provider's real response time for large projects, or that a deployment's provider honors cancellation promptly. The 20-minute hard cap remains a practical ceiling for sequential multi-batch jobs; the longer default accommodates healthy batches that exceed three minutes but does not guarantee completion for arbitrarily large source inventories. No paid/live model request was made for this mitigation.

## Review

### Mitigation and acceptance contract

Policy `review-2026-10-23-batched-coverage-v6` inventories CommonJS exports, exported class and prototype operations, direct local callees, routes and supported callbacks. It replaces the old 30-operation inventory ceiling with a 1,000-operation safety bound and explicit omitted-entry-point counts. Dynamic/computed exports and unresolved imported/runtime behavior remain unverified; this is not whole-program control-flow analysis.

`review/assessmentBatches.ts` plans requests containing up to eight operations and 64,000 source characters, capped at 128 requests. Each feature request retains its full related selected files so nearby safeguards are not removed. Remaining sources, including configuration and documents, receive independent sweeps. Large source-only documents split at original line boundaries, preserving all text and original offsets. An indivisible oversized source unit fails explicitly before paid execution; it is never silently truncated. Original requirement relationship provenance is included as relevance evidence, not proof of conformance.

Frozen sources are downloaded with four workers, verified against selected hashes, and reused by indexing and deterministic analysis. Rule start/completion audit events are bulk-persisted per source in chunks of at most 256; paid-request reservation and other events remain immediately durable. Full feature maps are stored initially/finally, with validated per-batch deltas during execution. Activity reconstructs the latest map without repeatedly storing the entire inventory.

Each stable batch has its own durable AI budget of at most five total attempts, including validation repairs, fallback and crash recovery. This bounds retries per distinct request, not the total number of legitimate batches in a Review. Invalid response shape, findings, source excerpts or feature references consume this same repair budget. Safe failure codes and usage are retained without logging provider payloads, source bodies or private reasoning. Malformed-response repair does not select a fallback provider; structured capacity failures stop immediately without retries or fallback. Earlier validated findings survive a later batch failure but never establish absence-based resolution. A restarted Review may re-execute earlier batches within their durable attempt budget; no exactly-once provider guarantee is claimed.

Only all-batch validated execution can emit `review_assessment_validated`. Unavailable selected inputs, truncated inventory, unsupported executable languages/parser errors or unverified executable assessments cannot qualify for a clean Review. JSON/YAML/HTML/CSS configuration and markup are intentionally outside the executable parser: their validated sweeps can complete, while map limitations remain and they do not acquire executable coverage or resolution proof.

### Finding accuracy

Executable JS/TS writes to `innerHTML` are source-backed sink candidates. Without an evidenced untrusted flow and failed safeguard they carry informational severity and low confidence, rather than an asserted high-confidence XSS vulnerability. Literal assignments, comments, strings and reads do not trigger the write checker. This is a syntax check, not taint analysis. TODO/FIXME/HACK markers ask the reviewer to establish policy and behavior context; a marker alone does not establish a release blocker. Other deterministic rules and semantic model validation remain in effect.
