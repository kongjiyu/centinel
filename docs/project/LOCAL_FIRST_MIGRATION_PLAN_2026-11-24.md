# Centinel local-first migration plan

Proposal · 24 November 2026

Start with one owner, one device, and one scoped Static Review. Import its project and exact source versions, run the Review from the desktop chat, restart Centinel, and reopen the saved findings, citations, and conversation with Supabase PostgREST and Storage blocked. Use this pilot to establish a local system of record before moving the remaining workflows.

Keep account identity and integration callbacks hosted. The initial release assumes a single-device workspace owned by one account. Shared projects, collaborator access, and live cross-device use need an explicit product decision before any affected project moves.

## 1. Define the storage boundary

| Area | Destination | Acceptance condition |
| --- | --- | --- |
| Projects and user context | Device database for projects, Check and Review references, requirements, standards, mappings, profiles and preferences used by the workspace, conversations, attachments, and permission decisions | Stable IDs preserve existing references. History, attached evidence, and continuation resolve within the active owner and project. |
| Runs and findings | Device database for Static Reviews, Dynamic and Auto Test runs, Readiness, findings and decisions, job leases, usage records, and audit events | Results and exact evidence remain accessible after restart. Partial, failed, paused, and unverified states retain their meaning. |
| Source and evidence bytes | Device files for original documents, frozen code, screenshots, traces, reports, and other evidence, with database manifests | Immutable versions keep their original IDs and verified bytes. A historical citation opens the version its execution inspected. |
| Retrieval and model settings | Device files for source indexes, vectors, and validated caches. Device database for provider settings, sync cursors, and index metadata. OS-protected storage for credentials and keys | Index identity binds owner, project, source hashes, policy, provider, and dimensions. Incompatible indexes rebuild only with the applicable provider budget and user settings. |
| Hosted account and integration control | Supabase Auth for sign-in, identity lifecycle, and session renewal. Keep public OAuth callbacks and provider-required exchanges or app secrets on the hosted integration service | Sign-in, reconnect, and unlink pass without hosted project data. Callbacks correlate to the initiating owner and device, reject replay, and store only the state required for the flow. |

GitHub, Drive, and configured remote model and embedding providers still need network access when used. Imported material stays usable locally during connector outages. A fully offline model workflow also requires a local provider. Browser runs need whichever target and browser dependencies their saved recipe specifies.

The existing storage failure and the Review evidence gap need separate acceptance checks. The `57014` history error identifies a canceled PostgreSQL read and is consistent with a statement timeout. The cause of that cancellation remains unconfirmed. The Review also recorded files whose conclusions failed semantic support. Local history removes the hosted query from the normal path. Review quality still depends on delivering the relevant frozen source and validating the cited lines. Keep both checks in the pilot. ## 2. Build the local storage foundation

1. **Inventory the current contracts.** Map every PostgREST table, Storage bucket or object family, RPC, realtime subscription, and hosted function reached by the desktop or sidecar. Record its owner and membership checks, writer, foreign keys or JSON references, and disposition. Include source sync, host-issued integration tokens, paid usage reservations, Review and conversation journals, and the existing device-local Check store. Baseline latency and failure codes on a representative project without logging prompts, secrets, or source bodies. [Supabase setup](../SUPABASE_SETUP.md) · [Conversation store](../../sidecar/src/conversation/store.ts) · [Source-index job store](../../sidecar/src/review/sourceIndexJobStore.ts)
2. **Give the sidecar one authoritative store per workspace.** Use embedded SQLite for structured records, with repository interfaces that preserve the desktop HTTP contract. Keep a single writer authority, enforce foreign keys and owner/project scope, index the bounded history and journal queries, and preserve revision checks, idempotency keys, and lease recovery. Put the store in the app data directory. Select and verify a bundled SQLite binding in a packaged Windows build before adopting it. Keep the legacy `sql.js` reader available for existing Dynamic data.
3. **Publish bytes and metadata recoverably.** Stage files and verify hash and length before publishing them under immutable local paths. Commit their database references after publishing the bytes, and reconcile interrupted writes on restart. Export a consistent SQLite snapshot with its referenced immutable files and a hash manifest. Exercise encrypted backup and restore, including recovery on a second device with an authorized owner and an explicit key-recovery procedure. [SQLite backup API](https://sqlite.org/backup.html)
4. **Carry authorization into the sidecar.** Bind the workspace to the verified hosted account ID and enforce owner/project scope on every local route, job, and evidence lookup. Authenticate the renderer-to-sidecar channel so another local process cannot call workspace routes by reaching the loopback port. Use OS protections for storage keys and local credentials. Keep service-role keys out of the desktop. Approve an offline unlock policy with bounded validity, lock on sign-out or account switch, and reconcile revocation when online.

The existing Static Review storage contract stays in force until the approved implementation updates it. Local SQLite is the proposed primary store for explicitly migrated workspaces. The current hosted path continues to serve workspaces before cutover. [Repository instructions](../../AGENTS.md)

## 3. Deliver the migration in phases

| Phase | Work | Exit gate |
| --- | --- | --- |
| 0. Inventory and fixture | Complete the dependency map, pick an owner-only fixture with a representative automation module, and capture counts, links, version hashes, and existing outcome states. | Every hosted dependency has a destination or a named release decision. The baseline records both known gaps and working behavior. |
| 1. Prove one complete local Review | Import a fixture project and frozen sources into a local workspace. Connect chat history, mode and scope selection, Review orchestration, deterministic findings, model-assisted evidence validation, and saved results. Use local Review and conversation journals. Pilot with direct reads from the explicitly scoped frozen files and embeddings disabled. | A desktop user can request and run a scoped Review. Local history and exact source citations survive restart with PostgREST and Storage blocked. |
| 2. Move remaining workspace workflows | Migrate source and document sync, Readiness, Dynamic and Auto Test history, reports, settings, model usage, and other workspace records. Reuse the existing on-device repository index. Replace its hosted retention prerequisite with verified local retention and capacity checks for local workspaces. Port validated cache reuse with its current compatibility and evidence rules. | All in-scope flows pass with hosted application-data endpoints blocked. Hosted sign-in and connector callbacks pass independent smoke tests. Existing legacy Dynamic data restores successfully. | 3. Rehearse on real data | Run a resumable import into an isolated workspace with user-authorized data. Reconcile counts, IDs, hashes, and historical links. All remaining exceptions have an agreed treatment before release. |

## 4. Import, cut over, and recover

1. **Export an authorized, versioned snapshot.** Enumerate the selected account and projects using their access rules. Capture PostgreSQL records and Storage object bytes separately with a manifest of schema version, UUID, timestamp, parent, byte length, and checksum. Record the export boundary. Reconcile updates and deletions during the final write freeze. Supabase database backups include Storage metadata, while the object bytes need a separate export. [Supabase backup documentation](https://supabase.com/docs/guides/platform/backups)
2. **Import into staging and resume by checkpoint.** Preserve IDs and history, including original correlation baselines, user decisions, citations, and incomplete runs. Validate owner, relationships, file hashes, and expected counts. Re-run the same import without changing counts or producing duplicates. Quarantine mismatches with a visible report. Preserve documented pre-existing missing evidence as missing. Activate indexes only when their compatibility metadata matches, and keep a rebuild explicit if it would trigger paid embeddings.
3. **Switch the writer.** Pause new hosted writes for the project and drain or explicitly checkpoint in-flight jobs before the final export. Reconcile the frozen hosted record against the staged local copy, take restore-tested backups, then activate the local copy. Retain the hosted copy read-only during the agreed recovery window. Treat active shared projects as a separate migration cohort once collaborative access has a defined replacement.
4. **Recover with post-switch work intact.** Before local writes, rollback can restore hosted write authority after deactivating the local copy. After local writes, stop new work and restore the local workspace first, then replay supported changes from the local journal. Returning authority to hosted storage requires a separately tested reconciliation of every local change since cutover. Keep both copies available until that reconciliation verifies.

## 5. Verify from the desktop

1. Sign in as the pilot account in the packaged Windows app. Open the migrated project and confirm the project, Review history, and source versions match the export manifest.
2. Block Supabase PostgREST and Storage for the app and sidecar while keeping Auth reachable. Ask in chat to review the automation module. If ORIN needs a mode or scope, answer in the non-blocking question container. Confirm the selection is saved and the workflow continues. With an ambiguous module, confirm ORIN asks for the missing scope directly.
3. Complete the Review with a controlled model fixture and a source finding with known exact lines. Verify that the run records analysis beyond deterministic SAST, that the saved evidence opens the exact frozen lines inline, and that an intentionally unsupported conclusion stays visibly unverified. Then verify source retrieval with a configured live provider as a separate test.
4. Restart Centinel and reopen the conversation, Review, source evidence, and run history. Repeat with Supabase application-data access still blocked. Confirm navigating away from the result stays on the selected page. Switch accounts and verify that the pilot's workspace and evidence cannot be opened by the second account.
5. Use a copy to interrupt import and Review execution, simulate a full disk, and restore the encrypted backup. Verify idempotent import, consistent database/file references, and truthful pending or failed states. Run the GitHub and Drive connection smoke tests with Auth and callbacks reachable.

Record the app build, fixture, manifest counts, denied network endpoints, provider mode, and pass or fail evidence for each check. Stop rollout if a historical reference changes meaning, project data leaks across owners, a resumed job repeats an already recorded paid call, or a migrated workflow contacts hosted application-data endpoints.

### Decisions before rollout

| Decision | Proposed default |
| --- | --- |
| Existing collaboration | Pilot with an owner-only project. Decide per shared project whether to retain hosted mode during transition or provide a replacement with equivalent access. |
| Offline access | Initial sign-in and account switching require Auth. Existing workspace offline unlock has a bounded policy approved before supporting it in production. |
| Backups and retention | Require tested encrypted export and restore. Agree on ownership, backup location, recovery expectations, and the hosted recovery window before production cutover. |
| Provider access | Preserve existing provider selection. Verify each connector and provider's credential exchange, renewal, and revocation before moving its local data path. |
