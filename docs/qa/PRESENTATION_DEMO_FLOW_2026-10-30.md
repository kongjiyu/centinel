# Centinel 演示流程（约 15 分钟）

主线只有一条：**需求 → 静态 Review 找到问题 → 把同一条需求交给 Dynamic Testing 在运行中的应用里验证 → 团队共享并导出报告。**

被测对象是仓库自带的 Todo demo app（`http://localhost:37702`）。它故意违反了 3 条需求，所以每一步都有真实结果可看：

| 需求 | demo app 的真实缺陷 | 谁能发现 |
|---|---|---|
| REQ-2 凭据处理 | 用户名和密码硬编码在前端 JS 里 | Review（静态） |
| REQ-3 安全显示 | todo 用 `innerHTML` 渲染，存在 XSS | Review（静态） |
| REQ-4 持久化 | todo 只保存在内存里，刷新页面后消失 | Review + Dynamic（运行时） |

素材：`sidecar/demo/REQUIREMENTS.md`（需求文档）、`sidecar/demo/index.html`（应用源码）。

---

## 一、演示前准备（提前 30 分钟完成）

> Review 一次需要大约 4–5 分钟，所以**正式的 Review 要提前跑好**。现场只演示启动界面，然后打开已跑完的结果。

1. 启动全部服务：
   ```bash
   pnpm dev
   ```
   确认 sidecar（37701）、demo app（37702）和桌面窗口都已打开。
2. 用测试账号登录（账号在 `.env.testing.local`）。
3. **Settings → Model Provider → Connect Codex**，用 ChatGPT 账号登录；Review 和 Dynamic testing 都选同一个模型，分别点 “Use for Review” 和 “Use for Dynamic”。
   - 检查：Home 上**不应该**出现 “Complete provider setup”。
4. **Projects → Create project**，命名为 `Todo App Demo`。
5. 进入项目 → **Source → Add source**，上传 `sidecar/demo/REQUIREMENTS.md` 和 `sidecar/demo/index.html`。
6. **Source → Manage requirements**：
   - Requirement candidates 选 `REQUIREMENTS.md` → **Extract candidates**；
   - 逐条 **Confirm**（REQ-1 到 REQ-5）。
7. **Review → Start a Review**：
   - 名称：`Todo app pre-release review`
   - 目标：`Verify the todo app against REQ-1…REQ-5: sign-in, credential handling, safe display of todo text, persistence and sign-out.`
   - 确认 Requirements 区勾选了 5 条需求 → **Start review**，等它进入 **Need Approval**。
8. （可选）在 Dynamic Testing 里提前建好环境，见第三部分第 2 步，现场可以节省 1 分钟。

## 二、静态 Review（约 6 分钟）

| # | 操作 | 要讲的点 |
|---|---|---|
| 1 | 打开 **Home** | Action required 只列真正需要处理的事项；失败后被 retry 覆盖的 Review 不会重复报警。 |
| 2 | 进入 `Todo App Demo` → **Source**，打开 `REQUIREMENTS.md` | 每个 source 都有版本和 hash。点 **Confirm still current**：文档时效确认和版本审批是两回事，90 天后会提示再次确认；**Mark deprecated** 的文档不会进入新的 Review。 |
| 3 | **Manage requirements** | 需求先由 AI 抽取为“候选”，人工确认后才算数。Review 只追溯已确认的需求。 |
| 4 | **Review → Start a Review** | 页面顶部的 “Recent Reviews” 列出了已有的 Review。如果模型没有配置好，Start 按钮会被禁用并给出 Settings 入口，而不是跑 15 秒后失败。演示到这里即可，不必真的启动。 |
| 5 | 打开提前跑好的 Review → **Overview** | 结论是 “Changes needed”，下一步按优先级排列：confirmed blocker → remaining risk → evidence gap。 |
| 6 | **Findings** → 打开 “Hard-coded credentials” 类的 finding | 每个 finding 都带 What to do / What is wrong / Where and why，以及引用的源码行（显示的是 `index.html:72`，不是内部存储路径）。规则引擎和模型对同一行的重复报告已合并为一个问题。 |
| 7 | **Traceability** | 5 条需求都有 Complete / Incomplete / Missing 状态。 |
| 8 | 点 **Approve review** | 因为有未解决的 Critical/High blocker，面板会要求写明理由并勾选确认才能批准。**点 Cancel**，说明人工决定仍然是最后一关。 |
| 9 | 点 **Export report** → Download PDF | 报告标题是 “Review report”，内容包括 scope、源文件版本、findings、traceability 和决定历史；Generated by 显示账号邮箱。 |

## 三、从 Review 到 Dynamic Testing（约 6 分钟）

| # | 操作 | 要讲的点 |
|---|---|---|
| 1 | 在 Findings 里打开 REQ-4（todo 不持久化）的 finding → **Verify with Dynamic Testing** | 跳到 Dynamic Testing，测试名称和目标已经预填，Criteria source 自动选为 “Requirements from a Review”。用的是 Review **冻结时**的需求快照，不是当前可能已经改过的版本。 |
| 2 | **Manage environments and local values → New environment**：名称 `Demo app`，网址 `http://localhost:37702/` → 展开 **Browser action permissions** → **Find controls** | 系统只读地打开页面一次，列出 `#username`、`#password`、`#login-btn`、`#todo-input`、`#add-btn` 等控件。勾选后点 **Allow selected controls**，再 **Save environment**。AI 只能操作这些被批准的控件，限制在代码层强制执行。 |
| 3 | Run environment 选 `Demo app`；把测试目标改为：`Sign in with username demo and password demo, add the todo "Buy milk", reload the page, sign in again and check that "Buy milk" is still listed.` | 演示用的账号是 demo app 公开的测试账号，不是真实凭据。 |
| 4 | Check 1：Requirement criterion 选 **REQ-4 Todos persist**，Verify 选 Visible text，Expected 填 `Buy milk` → **Save test** → **Run saved test** | 运行中显示 “Running · up to N steps”，不会提前显示 “Not tested”。 |
| 5 | 结果：**Failed** | 结论来自独立的 check，不是 AI 自己声称的结果。失败的 check 会**自动记录**为候选 finding，等待人工确认。Coverage 按 Review 里的需求统计。 |
| 6 | （可选）**Help** 页 | 覆盖 Review、Dynamic Testing、共享和模型设置。 |

## 四、协作（约 2 分钟）

| # | 操作 | 要讲的点 |
|---|---|---|
| 1 | 项目 → **Members** → 输入队友的 Centinel 账号邮箱 → **Add member** | 成员可以查看 sources、Review、测试和共享证据；只有 owner 能添加或移除成员。 |
| 2 | 点该成员的 **Remove** | 移除后立即失去访问权（数据库层 RLS 生效，不只是隐藏按钮）。 |
| 3 | 项目页 **Action → Export report** | 项目报告同时包含 Review 和最新的 Dynamic Run 结果。 |

---

## 五、收尾时主动说明的限制

- Review 是基于证据的静态分析，不保证覆盖所有运行时行为；Dynamic 只验证配置的 check。
- Project Assessment 的风险分数只来自 Review findings；Dynamic 的结果单独呈现，页面上有说明。
- Readiness 的 Coding standards 在没有专门规范文档时，可能仍被评为 Completed（已知问题，需要调整 prompt 并重新评测）。

## 六、现场出问题时的备用方案

| 情况 | 处理 |
|---|---|
| Codex 响应慢或失败 | 直接打开提前跑好的 Review 和 Dynamic Run；失败页面会给出 “Open Settings” 入口，可以顺势讲 provider 预检。 |
| demo app 没启动 | `pnpm --filter @centinel/sidecar demo` |
| 桌面窗口没打开 | `pnpm dev:check` 查看哪个服务没起来。 |
| Find controls 报错 | 先在浏览器访问 `http://localhost:37702/`，确认页面能打开。 |
