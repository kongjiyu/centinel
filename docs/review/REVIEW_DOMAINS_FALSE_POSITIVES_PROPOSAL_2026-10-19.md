# Review domain coverage and false-positive controls — proposal

**Status:** proposal for discussion; no analyzer or product behavior is changed by this document.
**Purpose:** prepare targeted Review-quality work after the current Project Readiness implementation, with special attention to JSON being mistaken for code and environment references or ordinary identifiers being mislabeled as leaked credentials.

## Scope and relationship to Project Readiness

The current Project Readiness contract remains the four evidence categories in [PROJECT_READINESS_SPEC_2026-10-19.md](../project/PROJECT_READINESS_SPEC_2026-10-19.md): Repository, Requirements, Design, and Standards. Readiness describes whether suitable project material is available and assessable. This proposal does not add a readiness score, a domain checklist to the readiness card, or an actor/permission completeness gate.

Security analysis may still identify authentication or authorization risks in a later Review-domain evaluation. That is a code or behavior concern supported by evidence, not a requirement to enumerate every actor and permission before a project is considered ready. The word **Personnel** below means risks in the application's human-facing flows and interfaces: confusing choices, accidental actions, missing feedback, recovery, and edge cases. It does not assess staffing, organizational processes, or staff judgment.

## Proposed rule and finding behavior

### Apply code rules only to code syntax

1. Resolve artifact format and language before running a rule. Run code complexity, call, and control-flow checks only when a supported code parser has produced the relevant syntax nodes. JSON, YAML, XML, environment files, Markdown, and other configuration or document formats get format-specific checks; their indentation, arrays, and nested objects do not count as code branches.
2. For a format or language without a parser, do not approximate code complexity by counting leading whitespace. Report the rule as not applicable or unavailable in the analysis inventory, not as a clean result.
3. Keep source location and rule provenance attached to each match. Semantic/model analysis may review JSON configuration for configuration risks, but it must identify the artifact as data/configuration and cite the exact value or property it assessed.

Parser-based structural matching follows the distinction in [Semgrep's pattern syntax](https://docs.semgrep.dev/writing-rules/pattern-syntax): rules match language constructs and can account for equivalent syntax. Where a check depends on values moving from a source to a risky destination, a source-to-sink model is a better fit than a name-only grep; [Semgrep's taint-mode reference](https://docs.semgrep.dev/writing-rules/data-flow/taint-mode/overview) describes sources, propagators, sanitizers, sinks, and traces. This is a design reference, not a decision to add Semgrep as a dependency.

### Distinguish credentials, references, identifiers, and placeholders

Use separate outcomes instead of one generic “hardcoded secret” verdict:

| Value class | Proposed treatment |
| --- | --- |
| Provider-specific credential-shaped literal | Emit a **candidate exposure** with the provider/rule, exact source location, format evidence, confidence basis, and redacted evidence. A local format check is not proof the credential is active. |
| Generic high-entropy literal in secret-bearing context | Emit a lower-confidence candidate. Entropy supports a finding but is not sufficient by itself; pair it with syntax, key/value context, known format, and nearby usage. Gitleaks documents measuring entropy on an extracted secret group, and GitHub separates generic, provider-specific, and AI-detected patterns with different precision expectations ([Gitleaks configuration](https://github.com/gitleaks/gitleaks#configuration), [GitHub supported patterns](https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns)). |
| Environment or secret-store reference | Treat process.env.X, os.environ[...], <ENV:X>, and equivalent parsed references as indirection, not as a credential literal. Assess a possible leak only when a sensitive value flows to an observable sink, such as logging, a public/client bundle, or an unintended external output. Show source and sink identifiers without displaying the value. |
| Application identifier or non-secret value | Do not report a leak because a property or variable is named token, secret, or password alone. A numeric tokenCount, secretEnabled, or a symbolic reference is not evidence of credential material. |
| Placeholder or example value | Recognize conventional placeholders and documented examples as context that lowers or removes a credential candidate, while retaining other checks. Do not treat placeholder words as a universal bypass: a real provider-format secret remains detectable even in a test or example file. |

Do not ignore test, fixture, sample, or documentation paths as a class. Such files may contain real credentials. Path and file role may inform confidence and the review explanation, but only a narrow, reasoned suppression may close an individual reviewed match.

Keep static confidence, verification, and runtime validity distinct:

- **Candidate / potential** means a rule or model identified a plausible concern that needs review.
- **Confirmed** means the stated property is directly supported by deterministic syntax/format evidence, a verified source-to-sink path, or human verification. The confirmed property must be named narrowly; for example, “credential-shaped literal is embedded in client code” does not imply “credential is active.”
- **Unknown validity** remains explicit unless a human-authorized, provider-specific live validity check is separately requested. This proposal requires no live credential probes. GitHub's validity-check documentation says those checks send credentials to the issuer; that is a distinct external action, not a static-analysis step ([GitHub validity checks](https://docs.github.com/en/code-security/concepts/secret-security/validity-checks)).

Confidence should explain its basis, for example provider_format + secret_context, source_to_sink_trace, syntax_only, model_inference, or human_verified. Model-only findings remain candidates unless independently verified. A valid artifact and line citation supports provenance but does not upgrade confidence by itself.

### Redact evidence and audit suppressions

- Redact secret candidate literals before constructing finding evidence, sending a finding summary to the model provider, persisting findings, rendering reports, or placing content in audit metadata. Preserve useful non-secret context, location, rule, and a short classification such as “credential-shaped literal redacted”; do not retain the raw secret in the evidence field.
- For source-to-sink findings, show source expression and sink call/site, not the value. Keep raw source available only through the existing authorized frozen-source access path; do not duplicate it into harness metadata.
- Suppression is per finding fingerprint and rule, with a required reason and reviewer note. Record its scope/source version, reason, decision time, and decision author in the reviewable audit trail. Avoid global file/path suppression that can hide a new credential. Semgrep's triage workflow is one precedent for distinguishing ignored findings by reason, including false positive and acceptable risk ([Semgrep finding triage](https://semgrep.dev/docs/for-developers/resolve-findings-through-app)).

## Domain check catalog and verification boundary

These four domains organize Review checks and evaluator labels. They are not new Project Readiness categories or a composite score. Each check should say which evidence it needs and whether it is static, semantic, or dynamic.

### Clarified intent: attack paths and human-error paths (19 October 2026)

Security should assess how a feature could be abused across its reachable paths and whether the safeguards actually protect those paths. Personnel should assess how a person could make a consequential mistake in a feature flow and whether prevention or recovery is effective. The user's rate-limiting and delete-confirmation/undo examples illustrate these principles; they are not universal requirements, exhaustive checklists or substitutes for the project's actual requirements, architecture and deployment evidence. Business and Technical retain the scope already proposed below.

For each security-relevant feature, build a scoped map of entry points, sensitive operations/data, dependencies and trust boundaries. Derive plausible misuse paths, including alternate endpoints, direct API access, background jobs and retries. Trace each path through the relevant enforcement points and record the source/configuration evidence, remaining assumptions, and uncovered branches. Assess prevention, containment and recovery where applicable. This is a proposed feature-level application of [OWASP threat modeling](https://community.owasp.org/Threat_Modeling), which relates threats, countermeasures and verification to a defined system scope. The review should identify known paths and coverage gaps; it must not claim proof that every possible attack path is secured.

For an illustrative availability path, examine whether repeated or expensive requests can exhaust a constrained resource. Assess applicable traffic limits, request-size bounds, concurrency/queue limits, timeouts and deployment protection. A rate-limiter declaration alone does not demonstrate coverage: inspect which routes use it, what identity/key it trusts, whether enforcement is shared across instances, and what happens on limiter failure. A verified gateway control may satisfy a need even when application code contains no limiter. Missing gateway evidence means unverified coverage, not automatically a missing control. Rate limiting alone does not establish DDoS resilience; application, session and network exhaustion need appropriate defenses ([OWASP DoS guidance](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html)). No live flood/load exercise is implied by this proposal.

For each consequential human action, map the intended goal, plausible accidental actions, affected objects, impact and reversibility. Evaluate whether the interface makes the target and consequences clear, provides a suitable decision or recovery point, communicates the outcome, and handles cancellation, duplicate input, stale selections and partial failure. For deletion, confirmation may be appropriate for irreversible loss; effective undo/restore may fit a reversible action. Do not require both or add a generic dialog to every low-impact action. Judge the actual safeguard: Cancel must leave data unchanged; confirmation must apply to the displayed target; undo must restore the affected state and communicate failures or expiry. W3C describes confirmation, correction and reversibility as error-prevention approaches; its broader [SC 3.3.6 explanation is Level AAA](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-all.html), used here as a design reference rather than a new conformance claim.

Each reviewed path should produce a concise evidence record: feature, domain, trigger, possible harm, expected safeguard and its basis, enforcement/recovery evidence, uncovered condition, assessment status and next action. Use statuses such as supported, gap, or unverified for coverage; finding verification remains separately candidate or confirmed as defined above. Publish a gap only with an explained scenario and evidence. Unread code, unavailable infrastructure configuration and unexecuted runtime checks remain explicit coverage limitations. User-facing activity may summarize the scenario and next check without exposing private model reasoning.

Proposed measurable additions to the mock acceptance set:

- A limiter that exists but is not applied to an exposed resource-intensive route is distinguished from a verified, applicable gateway limit; unavailable gateway configuration is marked unverified.
- Equivalent protected and bypassable feature paths receive different assessments with citations to the enforcement point and uncovered path. A source-only review never asserts that a deployment flood test passed.
- Irreversible deletion without a suitable decision/recovery safeguard produces a contextual human-error finding; deletion with effective confirmation or effective undo does not receive a blanket missing-dialog finding.
- A decorative confirmation whose Cancel still deletes, a changed selection between confirmation and submission, and an undo action that does not restore data produce specific findings. An effective safeguard passes only the named fixture checks.
- Every path record names scope, evidence and outstanding verification. No result label means exhaustive security or freedom from all human error.

| --- | --- | --- | --- |
| **Security** | Language-aware checks for credential literals/references, unsafe sources and sinks, validation/encoding, cryptography, session handling, exposed data, and relevant configuration. Use format-specific parsers for config. | Compare stated security requirements and data sensitivity with implementation/configuration; flag authn/authz, session, trust-boundary, and data-flow gaps with exact requirement and source citations. Keep unsupported suspicions as candidates. OWASP ASVS 5.0.0 is a versioned source of testable application-security requirements, not a claim of full ASVS coverage ([OWASP ASVS](https://owasp.org/projects/asvs)). | Only run authorized, scoped checks against an explicitly selected environment and test identity. Observe authentication/session/access-control outcomes and safe input handling. No active exploit research, arbitrary penetration testing, or credential-validity probes are implied. |

For every domain, not tested, unavailable, candidate, confirmed, and contradicted are evidence states, not scores. A finding linked to a requirement must cite that requirement and source version; a code-only concern must not acquire a fabricated requirement citation. Dynamic results must name the tested target/build and never imply that untested flows passed. This follows the PRD requirement to keep unsupported suspicions as candidates and preserve evidence limitations ([PRD STA-03 and STA-05](../Centinel_PRD_Revised.md#L108)).

## Fixed mock cases and measurable evaluation

Use versioned, locally stored fixtures with fixed adjudicated labels. Fixtures may contain synthetic credential-shaped strings solely to exercise matching; they must be visibly fictional, never copied from a user's configuration, and never sent to a live provider. No fixture is used for an issuer validity check.

| Case | Expected result |
| --- | --- |
| Deeply nested JSON objects/arrays with no executable code | No cq-deep-nesting or function-complexity finding; optional JSON/config checks remain eligible. |
| Equivalent deeply nested if/loop code in a supported language | One location-grounded complexity candidate with branch evidence, not a whitespace-depth claim. |
| const token = process.env.API_TOKEN and JSON {"secret":"<ENV:API_SECRET>"} | Environment-reference classification; no hardcoded-secret finding. |
| env.secret_value = "process.env.SECRET_VALUE", tokenName = "fixture placeholder", and tokenCount = 3 | No confirmed leak; if generic matching still emits a candidate, it must be low-confidence, redacted, and explained as a placeholder/name heuristic. Prefer no finding for the first two when parsed as a reference/placeholder. |
| test/ fixture containing a synthetic provider-shaped value such as AKIA0000000000000000 | Report a redacted candidate according to the provider-format rule. The fixture path does not disable scanning, and no network call occurs. |
| A synthetic generic secret-like literal in production-like code | Candidate with extracted-literal context/format and confidence basis; plaintext is absent from finding evidence, model summaries, logs, and reports. |
| Environment value used by a server-side request, versus the same value sent to console.log or included in a client bundle | Reference alone is not a leak. The logging/client-output case may produce a potential source-to-sink finding with both sites and no value. |
| X-Frame-Options: DENY and SAMEORIGIN; parameterized SQL; sanitized or constant innerHTML assignment | No blanket “disabled header”, SQL injection, or XSS claim. If context cannot be resolved statically, use a narrow candidate with the unresolved condition stated. |
| A genuine missing auth check or contradictory business requirement in synthetic code/specs | Preserve the issue as a security/business candidate with the exact route/source and requirement citations; static review does not assert runtime exploitability. |
| Confusing destructive-action label, no completion feedback, inaccessible status change, failed validation with no recovery, cancellation and retry paths | Record the specific user action, expected feedback, observed state, evidence, and recovery gap. No staff or organization-process judgment. |

Evaluate each deterministic rule and each domain against the same fixed, held-out fixture revision. Human adjudicators assign the reference labels and expected source/requirement locations before evaluation; model output must not be used to create its own ground truth. Report true positives, false positives, false negatives, precision, and recall per rule, language/format, and domain. Keep candidate and confirmed results separate. Mark zero-denominator measures N/A; never merge domains or review state into a project readiness/risk score.

Proposed initial release gates for high/critical deterministic rules are at least **95% precision** and **90% recall** on a fixture set with at least 30 positive and 30 hard-negative examples per supported rule/format combination. Generic heuristics can begin at **85% precision** and **90% seeded-positive recall**, with every false positive shown in the fixture report. These are proposed engineering gates, not industry standards; adjust them after the first labeled baseline. Report fixture counts and confidence intervals where sample size permits, and retain the raw confusion counts so a rounded percentage cannot hide misses or negatives. For model analysis, report its incremental true/false positives and false negatives separately from deterministic rules and require an evidence citation for every accepted finding.

Additional non-aggregate acceptance conditions:

- 100% of JSON-only nested-data fixtures produce zero code-complexity findings.
- 100% of synthetic secret positives stay detectable inside test/fixture paths; safe environment references and non-secret identifiers stay distinct from credential literals.
- 100% of finding evidence, model summaries, report output, and harness metadata in secret fixtures contain no candidate secret plaintext; the run makes zero credential-validity network requests.
- 100% of model findings with source locations point to a supplied artifact and in-range line, while the UI/report still presents model-only claims as candidates until independently verified.
- 100% of accepted suppressions have a non-empty reason and a finding-specific audit record; no blanket test-directory exclusion exists.
- Each domain mock packet contains both positive and negative examples, at least one explicit not-tested case, and evidence citations for any reported issue. A completed check means its stated test ran successfully; it does not mean every domain risk is absent.

## Later Review-workflow discussion boundary

See the [abstract workflow diagram and feature-path analysis proposal](REVIEW_WORKFLOW_ABSTRACT_2026-10-19.md) for the subsequent workflow discussion, including control flow, data flow and human-error recovery paths.

This proposal defines analyzer/evaluator semantics only. It does not change Review entry, stage progression, approvals, findings dispositions, reports, or UI placement. When the workflow is discussed later, the user-facing explanation should retain the existing separation between execution, human decision, and finding status, and should show candidate/confirmed state, evidence, source limitations, and recovery actions where a reviewer makes a decision. The existing workflow specification already requires inspectable findings and traceability before approval; this proposal does not replace it ([Review workflow evidence specification](REVIEW_WORKFLOW_APPROVAL_EVIDENCE_SPEC_2026-09-10.md#L30)).
