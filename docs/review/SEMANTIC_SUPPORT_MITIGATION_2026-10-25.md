# Semantic support mitigation — proposed implementation

Status: **specification plus isolated staged implementation**. The staged source and tests live only under ignored `evidence/public-repo-outcomes-2026-10-22/staged-semantic-mitigation-2026-10-25/`; no staged code has been applied to production. The active `review-2026-10-24-batch-domain-coverage-v9` runtime and its frozen acceptance runs remain untouched until the baseline owner releases them.

This plan follows [`SEMANTIC_GAP_REVIEW.md`](../acceptance/PUBLIC_REPO_ACCEPTANCE_V9_RESUME_2026-10-24/SEMANTIC_GAP_REVIEW.md). It adds a bounded consequence-support gate after frozen-source citation validation. It does not turn the syntax map into whole-program analysis, claim that a same-model challenge is independent evidence, or treat candidate verification as recall coverage.

## Observed contract and defect

`sidecar/src/review/assessmentValidation.ts` deliberately validates source provenance, not semantic truth. `validateFindingEvidence` checks the unique frozen artifact, version, line and exact excerpt; a source-valid finding is not proof that its consequence follows.

In `sidecar/src/review/orchestrator.ts`, each batch uses the stable stage `model_analysis` or `model_analysis:<batch.id>`. `guardMalformed` wraps provider `analyze`, validates finding shape/citations and domain coverage, and currently adds source-valid candidates to `lastSafePartial` before the batch response has passed all validation. The final response is then normalized and added to model findings. That is the promotion point the gate must protect; support failure must not re-add a rejected consequence from `lastSafePartial`.

`runModelOperation` in `sidecar/src/review/retry.ts` already provides the required paid-call boundary. It caps requests at five, writes a durable `in_progress` reservation before every provider call, includes successful calls, retries and fallback in the same total, and fails closed if persistence fails. `orchestrator.ts` obtains the current high-water mark through `getModelAttemptCount(review.id, operation)`. The Supabase implementation keys records by review and stage. A direct nested `provider.analyze` call would bypass these guarantees.

`planAssessmentBatches` in `sidecar/src/review/assessmentBatches.ts` already creates feature batches and source-only sweeps, but its sweeps contain only source segments not covered by a feature batch. Most executable files therefore receive map-focused four-domain assessment without an independent holistic source pass. That is a separate recall limitation; candidate support cannot find issues the generation pass omitted.

`resumeQueuedReview` replays frozen inputs. It does not persist raw model output. Compute a deterministic identity from the normalized candidate and frozen source versions for audit/replay comparison, but do not add a verdict cache in this first patch. A crash consumes durable reservations; replay cannot reuse an unrecorded response or reset the budget. If the regenerated candidate cannot be fully challenged with the remaining calls, it stays unverified and requires a manual new Review.

## Proposed gate

1. Keep the existing response-shape, domain-coverage, frozen-source and `findingsWithinBatch` checks. After those checks, assign each candidate an opaque stable ID derived from the batch ID and every promoted public field: title, description, recommendation, severity/category/confidence, domain/type, causal steps, primary and related validated references, and exact authority IDs. Cap the support packet at 32 candidates per batch and 2,000 characters per candidate field/reference; exceeding a cap is an explicit unverified assessment, never silent truncation.
2. Send one bounded support challenge per candidate packet using the same configured provider/model that produced the accepted generation response. If generation succeeded through the existing configured fallback, use that same selected provider for the challenge. Do not resolve a new provider, change model, or add a new fallback path.
3. The challenge returns exactly one row for every candidate ID: `claimBoundary` (`local_source`, `selected_call_path`, or `runtime_dependent`), `disposition` (`supported`, `contradicted`, or `insufficient`), a concise public trigger/consequence, exact source evidence references with roles (`entry`, `guard`, `sink`, `counterevidence`, or `contract`), exact authority references when a finding cites a confirmed requirement or enabled standard, and a short public limitation when insufficient. It receives the current `AssessmentBatch.sources`, normalized candidate claims, and relevant already frozen confirmed requirements, enabled standard rules, reviewer dispositions, and traceability mapping IDs/versions from the generation request. It must not use unconfirmed requirement candidates as authority. A requirement-backed issue must cite both the source behavior and the exact trusted requirement/rule record; a manual confirmed requirement does not need to masquerade as an artifact line. It must explicitly test the strongest supplied guard/counterexample, including short-circuiting, inherited properties, selected arguments and normalization where present. A missing safeguard or unselected caller is never itself proof.
4. Validate the challenge as untrusted model output. Require exact candidate-ID coverage with no missing, duplicate or unknown IDs. Require every supplied source reference to identify an existing frozen artifact, exact content hash, original path and line/excerpt; reuse `validateFindingEvidence`'s source checks and `findingsWithinBatch`'s range check through a small shared reference helper. Validate authority references separately against the frozen trusted IDs and all available version fields, never against model-supplied names alone. Require relevant source evidence for `supported` and `contradicted`; an `insufficient` row may have no additional source reference when the missing item is precisely an unavailable caller/runtime boundary. Do not accept a role label as semantic proof.
5. Only a `supported` candidate may enter model findings or safe partial retention. Keep its original candidate claim intact: this first version does not ask the gate to rewrite or synthesize a different finding. A separate, source-supported local behavior must be represented by its own candidate; a combined local/application claim that cannot be separated is insufficient. Drop contradicted candidates from actionable findings. For an insufficient `local_source` claim, retain only a public, bounded limitation, mark the affected local feature/domain unverified, and fail that batch's model assessment. For an insufficient `selected_call_path` or `runtime_dependent` claim, drop the actionable allegation, retain an explicit public boundary limitation, and withhold its primary artifact, every related/support reference, and affected mapped-path artifacts from absence-resolution proof; an adequately evidenced local four-domain assessment may still complete as `potential_gap`. Never convert either case to `no_issue_identified`, clean coverage, or absence proof. Preserve separately supported local siblings, but revoke a previously accepted support row if a later repair contains a duplicate or conflicting row for that same candidate ID.

The challenge is a consistency check by the configured model, not independent corroboration. It can still repeat the original reasoning error. No schema, instruction, fake provider, or matching same-model answer is sufficient evidence of semantic accuracy; acceptance requires the blinded evaluations below.

## Five-call ledger and recovery

Use the existing batch operation key for generation, all generation repairs, support challenge, and support-response repairs. Do not introduce `semantic_verify:<batch>` or per-candidate attempt budgets.

| Request group | Maximum allocated calls | Existing mechanisms |
| --- | ---: | --- |
| Generation, citation/domain repairs, configured fallback | 3 | `runModelOperation`; existing stable batch stage; durable reservations |
| Support challenge and bounded malformed-response repair | 2 | a second `runModelOperation`; fresh `getModelAttemptCount`; same stable batch stage |
| Total | 5 | hard cap in `runModelOperation` |

Set the generation operation's `maxTotalAttempts` to three, including its current fallback reservation rules. After it returns, read the durable count again and run the challenge with `maxTotalAttempts: 5`, `attemptOffset` equal to that fresh count, and no fallback. Route both through the existing `onAttemptStarted`, `onAttempt`, `onRetry` and cancellation callbacks. The operation stage string must be identical for both calls. Any successful generation request, malformed repair, fallback request, challenge or challenge repair consumes one of the five slots.

Wrap support response validation the same way `guardMalformed` wraps citation/domain validation: on safe schema/reference errors, raise a bounded malformed `ModelProviderError` so `runModelOperation` can use an eligible remaining slot with a repair prompt containing only trusted candidate indexes and allowlisted feedback codes. Never include rejected model text in repair feedback or audit events. If generation uses all three slots and the challenge uses both, no other request may run. Exhaustion, context-limit failure, malformed challenge, missing identity, or a crash after a durable reservation leaves that candidate unsupported. A crash can consume a reserved slot without a response; it cannot create another free request.

If a response has some individually valid support rows but fails packet coverage, keep only the individually validated supported rows as safe partial siblings; duplicate rows invalidate that candidate ID. Repairs may fill missing rows, but a valid candidate whose disposition or claimed boundary changes across repair packets becomes a conflict: remove any positive partial, retain a neutral limitation, and exclude affected artifacts from absence proof. The same exact public claim with conflicting results across feature and source-sweep packets also becomes a conflict; do not fuzzy-merge different claims. If repair/capacity ends first, preserve supported siblings and earlier completed batches, but mark missing/insufficient local rows unverified and prohibit absence-based resolution. A boundary-only caller/runtime limitation may leave an independently evidenced local assessment complete while withholding the affected artifact's absence proof.

## Persistence, compatibility and privacy

No schema migration or new finding field is required. Persist only safe support metadata in existing `audit_events`: policy/version, batch ID, opaque candidate hash/index, boundary and disposition enums, reference count/hash, outcome counts and bounded duration/attempt data. The reference identity hash covers canonical validated artifact/hash/path/line identities, excerpt hashes, and frozen authority IDs/versions; it never stores raw excerpts or authority text. Never store raw candidate descriptions, source excerpts/bodies, prompts, rejected provider text or private reasoning in harness/audit metadata. Support references remain in the frozen-source validation path; the durable support event stores only a stable hash of their identity. A new policy/runtime request continues to use the user's configured provider and model.

Add support event types to the existing `getHarnessEvents` allowlist so reviewers can inspect the safe outcome counts. Do not add a repository read path or verdict cache solely for recovery. Existing immutable findings and v9 results are not rewritten.

Increment `STATIC_REVIEW_MODEL_POLICY_VERSION` to `review-2026-10-25-semantic-support-v10` and `ASSESSMENT_VALIDATION_VERSION` to `static-assessment-2026-10-25-semantic-support.1`. Bind new resolution eligibility to that exact assessment version; old validation provenance cannot mint a new proof. Existing stored findings and historical correlation records remain present, but old proof versions do not qualify as current absence evidence. Incomplete/insufficient support omits the validated assessed reference or marks it unverified, so current finding correlation cannot resolve old issues on absence.

Add bounded harness steps such as `challenge_support` and `validate_support`; expose only safe indexes/counts, disposition counts, duration and policy version. Keep public limitations concise and distinct from private model reasoning. Capacity classification and `provider_paused` propagation must remain the existing behavior: stop later batches and all challenge/repair/fallback requests immediately on structured capacity errors; a generic 429 alone is not exhaustion.

## Separate recall mitigation: full bounded source sweeps and contract comparison

The candidate gate can only accept, narrow or reject candidates that generation already returned. It cannot discover an omitted issue. Keep recall mitigation as a separate workstream.

Extend `planAssessmentBatches` to add source-only semantic sweep batches for **all selected executable source segments**, including segments already present in feature batches. Keep `featureAssessments: []` for these batches. They inspect source semantics independently but do not add four-domain coverage, set `assessedArtifactIds`, or certify executable absence. They may contribute individually supported findings through the same citation and consequence-support gate.

When selected source files in the same bounded sweep disclose a common explicit contract (for example, a declared option or interface) and multiple selected implementations, add a general instruction in `buildModelRequest` to compare the implementations with that declaration and each other. Pair only contracts and implementations evidenced by the already selected frozen files, using existing bounded module/export information where available. Do not traverse arbitrary callers, fetch dependencies, follow README links, infer a defect in an unselected implementation, or exceed the source/context limits. Require exact references to both the declared contract and selected implementation. Treat documented/intended differences as non-issues, and mark comparisons unverified when the full pair does not fit instead of silently omitting one side.

All feature batches and source-only sweeps must be planned before provider resolution/calls, with the combined count within the existing 128-batch ceiling and each request within 64,000 source characters. If adding the sweeps exceeds either bound, fail the Review before any provider request and preserve explicit scope/limit evidence. Do not split a declaration from its selected implementation merely to fit; deterministic batching may group only evidenced selected peers and must fail closed when a complete group cannot fit. The extra sweeps increase configured-provider request and token cost; record batch counts and source ranges, and expose no invented metrics.

This instruction is not recall acceptance evidence. Test it with separate miniature fixtures for (a) a real selected implementation omission, (b) an intentional/documented difference, and (c) an omitted implementation that is unselected. Use different identifiers and shapes from any registered public benchmark. Fake-provider prompt assertions verify plumbing only; a separately recorded blinded evaluation must grade discovery, causal evidence and abstention. If the bounded-packet prompt misses those cases, consider a later exact-name/type-based contract-pair inventory limited to already selected source files; do not add general caller expansion as the first response.

Do not import the public-repository benchmark manifest, issue text, adjudication, expected labels, or target names into production code, prompts, tests, or app data. The prospective `SEMANTIC_SUPPORT_CONTROLS_2026-10-25` corpus is a separate offline evaluation artifact: keep its answer key out of the model packet and out of runtime inputs. Its README describes integrity/blinding controls, not production gate evidence.

## Tradeoffs and blockers

- Reserving two of five requests for support reduces generation/repair/fallback capacity to three. A generation that cannot complete in that allocation fails closed rather than borrowing the challenge budget.
- A second invocation by the same configured model can repeat the original error. Only outcome-based evaluations can show whether the gate improves precision, and contract-recall testing must remain separate.
- Source-only evidence cannot establish browser, process resource thresholds, deployment trust or external runtime behavior. Such claims remain insufficient without already authorized reproduction evidence; their unsupported consequence is dropped and must not block independently evidenced local assessment or be treated as clean absence.
- Challenge prompt overhead can exceed a review's configured context budget even when generation fit. The gate must stop before provider access, preserve already supported siblings, and record an unverified outcome; never truncate guards or source silently.
- The current production code and active v9 runtime were not edited or invoked. Staged source/test checks are not a production implementation result or a semantic-quality claim; the candidate challenge and recall mitigation still need independent review and blinded evaluation.
